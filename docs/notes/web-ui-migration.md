# Pinky desktop UI → Wails + React (full replacement)

**Audience:** implementer AI / engineer on fork `tarou-jp/smartphone-agent` (`main` as of 2026-11-10, commit `277f327` and later).

**Decision:** Replace the entire MyGo desktop UI (`ui/`) with a **Wails** shell and a **React + TypeScript** front end (Vite; Next.js not required). **All Go below the UI stays:** `internal/gateway`, drivers, MCP, policy, `internal/inapp`, `cmd/pinky` daemon/MCP paths.

**Do not** change upstream `DIYgod/pinky` until the fork is stable. Read [WORKING.md](../WORKING.md) and [client.md](client.md) before editing.

---

## 1. Goals and non-goals

### Goals

- Cursor-class **in-app chat / composer** (queue, Steer, Stop, streaming, scroll) and room to match Cursor visuals with CSS.
- **Parity** with current MyGo client behaviour documented in [client.md](client.md): mirrors, approvals, Needs you, Activity, Settings, Add phone, menu bar, notifications, global Stop-all shortcut, background/hidden start.
- **One process** for the desktop app: gateway + UI (same as today’s `pinky` / default command).
- **Locales:** en, ja, zh-Hans (reuse strings from `cmd/pinky/locales/*.json` or migrate to `react-i18next` JSON derived from them).

### Non-goals (first release of web UI)

- Replacing **MyGo** in the **release pipeline** on day one (phased; see §6).
- Putting **API keys or PINs** in the front end or `localStorage` (all via Go + OS keychain).
- Changing **agent-facing** MCP semantics or `gateway.API` contract for external agents.
- Electron.

## 5. Go ↔ frontend contract

### 5.1 Wails bindings (sync RPC)

Use for short calls with clear JSON structs:

- `GetDevices()`, `GetTasks()`, `GetNeeds()`, `GetSettings()`, `SaveSettings(partial)`
- `Decide(needID, decision, note)`, `Unlock(deviceID)`, `TakeOver`, `HandBack`, `Stop`, `StopAll`
- `Touch`, `Key`, `Text` (mirror input)
- `RevealModelAPIKey(provider)` → Go only; never return key to logs
- `ChatSend(sessionID, text, deviceScope)`, `ChatStop()`, `ChatQueue*`
- `Quit()`, `OpenPath`, `ExportHistory`, etc.

**Subscriptions:** Prefer **Wails runtime events** (`runtime.EventsEmit` / `OnEvent`) for:

- `gateway.Event` stream (devices/tasks/needs changed) — mirror today’s `Subscribe`
- Toast messages, update available

### 5.2 Streaming (chat + agent progress)

- **Server-Sent Events** or **WebSocket** on loopback (e.g. `127.0.0.1:0` chosen by Go, URL passed to front end at startup).
- Events: `chat.token`, `chat.tool`, `chat.done`, `chat.error`, `chat.cancelled`.
- Must match behaviour in current `ui/chat.go` (single streaming bubble, queue flush, interrupt).

### 5.3 Mirror video (critical path — spike in Phase 0)

Today: `gateway.API.Stream` → FFmpeg decode → `mg.Bitmap` ([ui/mirror.go](../../ui/mirror.go)).

**Options (pick one in Phase 0 spike; document FPS/latency/CPU):**

| Option | Pros | Cons |
|--------|------|------|
| **A. JPEG/PNG frames over WS** | Simple | Bandwidth/CPU heavy at 60fps |
| **B. H.264 fMP4 or raw NAL over MSE** | Efficient | More JS plumbing |
| **C. Offscreen native child view** | Best perf | Breaks “all web UI” purity; platform-specific |
| **D. Canvas + RGBA shm from Go** | Medium complexity | Wails custom asset / shared buffer APIs |

**Acceptance for mirror:** Same perceived latency as MyGo on one iPhone + one Android fake; touch mapping correct; agent overlay (target box) if kept in MVP.

### 5.4 Secrets

- All `secret.Store` / Touch ID / Windows Hello flows stay in Go.
- Front end receives **boolean** `hasAnthropicKey`, not the key.
- Same session cache semantics as `ui/model.go` `revealModelAPIKey` (optional).

## Status (2026-11-10, branch `wails-react-ui`)

The web client exists and covers the main screens; the MyGo client stays, behind `-ui mygo`, until the parity checklist (§8) passes on real phones.

### What was built, and how it differs from the plan above

- **`internal/deskapi`** (pure Go, no cgo): an HTTP server on `127.0.0.1:<random>` over `gateway.API` and the gateway's extras (the same type assertions as `ui/extras.go`). JSON views in camelCase (`views.go`), Server-Sent Events for changes (`/api/events`: `change`, `settings`, `mirrorSize`, `diskImage`), MJPEG for the mirrors (`/api/devices/{id}/mirror`, decoded with `internal/video` at the phone's own size and scaled to the box; touches go as fractions of the screen, `nx`/`ny`), and the in-app chat as an SSE stream per message (`POST /api/chat`). Mirror option A of §5.3, chosen for now: it needs no JS decoder and plays in an `<img>`.
- **Security:** the window opens `/?token=…`, which the server trades for an HttpOnly, SameSite=Strict cookie (`pinky_token_<port>`); every `/api` request needs it (or `X-Pinky-Token`), and any Host but 127.0.0.1/localhost is refused (DNS rebinding). PINs and model API keys never leave Go: the client only learns whether one is saved. `/api/open` opens only the rules files and exports.
- **Settings types** moved from `ui` to `deskapi` (`ui` keeps aliases), so both clients and `cmd/pinky` share `settings.json`'s format.
- **Window:** `internal/webshell`. With the `wails` build tag (and cgo) it is a Wails v2 window whose page forwards to the loopback server, so the front end speaks plain HTTP in the window and in a browser alike, and Wails bindings are not used. Without the tag (every `CGO_ENABLED=0` build) it opens the browser.
- **`-ui` flag** on `pinky`: `auto` (default) picks the web client when the build has the Wails window and the built front end (`make web-app`), else MyGo — so `go tool mygo build` and the release pipeline still ship the MyGo client, unchanged. `-ui web` and `-ui mygo` force one.
- **Front end:** `ui/frontend` (the plan said `frontend/`): React 19, TypeScript, Vite 6, **MUI 6** (not Tailwind). Words come from the MyGo catalogs (`cmd/pinky/locales/*.json`, read by a small ICU formatter, `src/i18n/icu.ts`), so both clients say the same; words only the web client has are in `src/i18n/web/*.ts`. `src/lib/gwtext.ts` ports `ui/gwtext.go` (the gateway's English steps, approvals and status lines in the app's language).

### Agent panel (in-app chat)

The chat is the window's, not a phone page's: `components/chat/AgentPanel.tsx` at the right edge of every page, after Cursor's agent panel. `ChatProvider` (`components/chat/store.tsx`) holds the chats, so a run goes on while the person moves between pages. Wide windows (≥ 1240 px) give it a column that its left edge resizes (320–640 px); narrower ones lay it over the page. ⌘L shows it and focuses the composer; a hidden panel leaves a button in every title bar.

- **Phones as context.** In Agent mode the composer's pills are the phones the message goes to: the phone on screen is offered (dashed) as Cursor offers the open file, and @ adds phones (or all connected). Ask mode only talks.
- **Several phones.** One `POST /api/chat` with `devices`: the server runs one agent per phone side by side in that one stream (a stream per phone would take the connections the MJPEG mirrors need), tagging each event with `deviceId`; `run_end` ends a phone's run and `done` the last. The thread shows a tab per phone above their runs.
- **Steps.** `inapp.AgentEvent` now says what each tool call does (`tool_start`/`tool_end` with the tool, the agent's intent, its arguments and the result's status, and `text` for what the model says between calls); the server sends them as `step` events beside the plain `progress` lines. The thread draws each as a Cursor-style row.
- **Follow-ups.** The agent gets the chat so far (`AgentConfig.History`), not only the last prompt.
- Chats are kept in this browser's storage (`pinky-chat-v2`; the first format is migrated).
